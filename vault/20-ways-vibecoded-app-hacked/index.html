20 ways someone hacks your vibecoded app

The video's list, written out. 20 things someone can do to a live app, each with the real case behind it (Next.js, Tea, Stripe, Verizon, OWASP) and the fix. Plus one prompt that checks your own app for every one and reports before it changes anything.

This is the page for anyone who commented PATCH. The prompt is right below. Paste it into Claude Code or Cursor opened in your project, tell it what your app does, and it checks your code and config against all twenty and reports before it touches anything.
Paste into Claude
My app is: [one line on what it does, and the stack: framework, host, database, auth, payments].

Go through the 20 items below. For each one, tell me whether it applies to my app and how you can tell from the code or config, then what the fix would change. Report on all 20 first. Fix only the ones I approve, one at a time, and run the project's checks after each. Don't install anything, don't change or rotate any keys, and don't touch production without asking me first. Some of these are DNS, hosting, or provider settings rather than code. For those, tell me the exact setting to check and I'll do it.

The 20:

1. Auth checked only in Next.js middleware. If login is gated in middleware alone, check the Next.js version and move the check into the route or server action.
2. The .git folder served in production. Make sure the live site doesn't hand out .git. Deploy built output only, block /.git, and rotate any key ever committed.
3. Open storage or database rules. Check Firebase/Supabase storage and row rules aren't left open. Keep buckets private, scope policies to the owner, and tighten rules before deploy.
4. Price trusted from the browser. Confirm the server recomputes the amount. The client should send a product id, not a price.
5. Login with no defense against credential stuffing. Check for per-user and per-IP rate limits, MFA, and a breached-password check.
6. A database reachable from the internet. Check nothing is bound to a public interface without auth, and that a backup restores.
7. Third-party scripts loaded from a CDN. List external scripts; self-host or pin them with Subresource Integrity, and drop abandoned ones.
8. Send endpoints with no limit. Rate-limit anything that sends an SMS or email, and cap which countries you send to.
9. An AI feature with too much access. Give it the least access it needs, keep secrets out of its instructions, and make it ask before anything it can't undo.
10. A weak or hardcoded JWT secret. Use a long random secret from the environment and verify the signature on every request.
11. Race conditions on limits. For one-time codes, balances, and quotas, make the check and the update one atomic step in the database.
12. No email verification on signup. Verify the email before the account can be used, and handle social-login merges safely.
13. DNS records pointing at deleted services. Check for subdomains that still point at something you removed, and delete the record.
14. Server-side fetches of user-given URLs. Don't fetch user-supplied URLs from inside your network; require IMDSv2 on AWS.
15. User input reaching filesystem paths. Don't pass user input to file APIs, and keep the server and its software patched.
16. Reset links built from the Host header. Build password-reset links from config, not from the request's Host header.
17. Source maps shipped to production. Don't publish production source maps, and check what a package contains before you publish it.
18. No framing protection. Send X-Frame-Options or a CSP frame-ancestors header.
19. Redirects built from user input. Don't redirect to a URL taken from the request; check it against an allowlist.
20. Login, signup, and reset that leak which emails exist. Return the same generic response whether or not the account exists.

Run it in Claude Code, Cursor, or Codex opened in your project, so it can read the code and the config. A few of these live outside the code, in your DNS, your host, or your database provider's dashboard, so the prompt asks it to point you at the setting instead of guessing.

Below is what each of the twenty is, the real case behind it, and the fix. These are public findings from the sources named. Check each source for the latest.

1. Skip your login with one header (Next.js)

If an app does its login check inside Next.js middleware, a crafted request could skip that check. The advisory rates it CVSS 9.1, critical. Vercel's writeup says Next.js uses an internal header to detect recursion, and that middleware should not be the only thing protecting a route. The fix: upgrade to a patched Next.js (12.3.5, 13.5.9, 14.2.25, 15.2.3, or later) and check authorization in the route itself, not only in middleware.

2. Download your whole .git folder

A site that serves its own .git folder hands out the full history of its code, including keys that were deleted from the current files but still sit in old commits. Intruder scanned 3.5 million hosts and found 28,000 exposed repositories, pulled 107 live Stripe secret keys, a few still valid, and over 400 AWS keys. The fix: deploy the built output and never the project folder, block /.git on the server, and rotate any key that was ever in the repo.

3. Read your storage straight out of the bucket

Storage or database rules left open let anyone read what's inside. Tea had what its own statement called a legacy unprotected Firebase storage bucket, and about 72,000 images leaked, including roughly 13,000 selfies and photo IDs. Firebase's docs warn that once you deploy, the app is publicly accessible even before launch, so update your rules first. Supabase says the same about public buckets: anyone with the file's URL can read it. The fix: keep buckets private, which is the default, and allow reads with a policy scoped to the owner or with signed URLs.

4. Change the price at checkout

If the price comes from the browser, a customer can change it before it reaches your server. Stripe's own docs say to recalculate amounts on the server and not to trust client-provided prices or totals. The fix: the browser sends a product id, your server looks up the price, and your server creates the payment.

5. Stuff leaked passwords into your login

Bots take email and password pairs from other sites' breaches and try them against your login. OWASP calls it testing username and password pairs obtained from the breach of another site. Verizon's DBIR put the median daily share of credential stuffing at 19% of all authentication attempts, and about 12% even at small businesses. The fix: rate-limit login per user and per IP, turn on your provider's breached-password check, and push people toward MFA.

6. Wipe your open database

A database left open to the internet with no password gets found by a script and emptied. In the 2020 Meow attacks, almost 4,000 databases were deleted in a weekend by an automated script that, as researcher Bob Diachenko described it, overwrites or destroys the data completely. The fix: keep the database on a private network behind your app, with a password, and a backup you have actually tried restoring.

7. Inject malware through a script you embed

A third-party script you load from someone else's domain can be changed under you and run on your visitors. Sansec reported that the cdn.polyfill.io domain, embedded by over 100,000 sites, was caught injecting malware on mobile devices through any site that embedded it. The fix: host your own copies of the scripts you depend on, or pin them with Subresource Integrity, and remove ones that are no longer maintained.

8. Run up your SMS bill

Bots hit your "text me a code" button over and over, and you pay for every message. Twilio describes SMS pumping as bots flooding any public entry point that triggers an automated message, and your business pays for every one sent. The fix: rate-limit the endpoint per number and per IP, add a delay between requests, and cap the countries you send to.

9. Make your chatbot leak its instructions

Text a user types, or text sitting on a page your AI reads, can change what your AI feature does. OWASP's LLM01 lists leaked system prompts and access to functions the user shouldn't reach among the impacts, with layered defenses like least privilege and human approval for risky actions, and notes no method is known to be foolproof. The fix: give the AI feature the least access it needs, never put a secret in its instructions, and make it ask before doing anything it can't undo.

10. Forge a login with your JWT secret

If the secret that signs your login tokens is guessable, an attacker can make tokens that claim to be anyone. PortSwigger notes it can be trivial to brute-force a server's secret from a wordlist of well-known ones, and that a forged token lets an attacker escalate their own access or impersonate other users and take over their accounts. The fix: use a long random secret, keep it out of the code, and verify the signature on every request.

11. Redeem your discount code over and over

Requests fired at the same instant can beat a limit your code checks one at a time. PortSwigger's example is a store's one-time promo code redeemed again and again, and the same flaw can push a balance below zero. The fix: make the check and the update one atomic step in the database, rather than reading, deciding, and writing in separate steps.

12. Sign up with your email before you do

An attacker creates an account with your email before you get there, then takes it over after you've started using it. The USENIX study of 75 popular services found at least 35 open to one or more of these account pre-hijacking attacks, where the attacker acts before the victim creates the account. The fix: confirm the email before the account can be used, and when someone later signs in with Google or another provider, don't quietly merge it into that unconfirmed account.

13. Take over your forgotten subdomain

A DNS record still pointing at a service you deleted lets someone else claim that address. Silent Push isolated 16,000 dangling subdomains across 12,500 domains and automated the takeover of 4,000 of them: the hostname still answers, but the service it points to is gone. The fix: delete the DNS record when you delete the project it pointed at.

14. Make your server fetch its own cloud keys

A feature that fetches a URL you hand it can be pointed back at the server's own cloud metadata address. AWS explains that these SSRF flaws let an attacker make requests from inside your app, and that the metadata service can hand out the credentials for any role attached to the instance. The fix: don't fetch user-given URLs from inside your network, and require IMDSv2, which AWS says blocks the large majority of SSRF attempts.

15. Read your server's files with ../

Putting ../ in a filename or URL can step outside the folder you meant to serve. PortSwigger says these let an attacker read arbitrary files on the server. The Apache flaw CVE-2021-41773, which Apache marked critical, was a path traversal and file disclosure bug that could reach remote code execution where CGI was enabled. The fix: don't pass user input to filesystem APIs, and keep the server and its software patched.

16. Send your password reset link to their server

Changing one request header can make your reset email point at the attacker's site. PortSwigger describes modifying the Host header so it points at a domain the attacker controls, so the reset token gets delivered to the attacker's server. The fix: don't build links from the Host header; keep your own domain in config and build the link from that.

17. Read your source code from your source maps

A source map left in a published build lets anyone rebuild your original code. The Hacker News reported that a Claude Code npm package shipped a source map that could be used to read its source, nearly 2,000 TypeScript files and over 512,000 lines; Anthropic called it a release packaging mistake from human error, not a breach. The fix: don't publish source maps for production, or check what your package actually contains before you publish it.

18. Put your site in an invisible frame

Your page gets loaded invisibly over another one, so a click a visitor thinks lands on the top page actually hits a button on yours. OWASP calls this clickjacking, or a UI redress attack, where transparent layers trick a user into clicking something they didn't mean to. The fix: send the X-Frame-Options header or a CSP frame-ancestors rule so your page can't be framed by other sites.

19. Bounce your users to a phishing page

A link on your own domain can forward a user to the attacker's site. OWASP describes an open redirect where a malicious link sends your users to an unvalidated site and launches a phishing scam to steal their credentials, under the trust of your domain. The fix: don't build redirects from user input, or check the destination against an allowlist of places you're willing to send people.

20. Find out which emails have accounts

If login, signup, or reset says something different for a real email than a fake one, anyone can test a list and learn who has an account. OWASP's rule is that the app should respond the same way, in both the HTTP response and the page, whether or not the account exists. The fix: give the same generic message every time, across login, signup, and password reset.

Save this one. Run the prompt before you ship, then again after every big feature. It reports first, so nothing changes until you say so.
